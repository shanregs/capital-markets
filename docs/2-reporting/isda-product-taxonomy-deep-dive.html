01 · Two things "ISDA" means

What Is the ISDA Product Taxonomy? — Origin, Purpose & the Two Things "ISDA" Means

ISDA standardizes two genuinely separate things people conflate: the Master Agreement (a legal contract template) and the Product Taxonomy (a classification scheme). This module is about the second.

ISDA standardizes...What it isCovered in
The ISDA Master AgreementA legal contract template two counterparties sign once, governing every OTC trade between them (netting, default, collateral)Module 12
The ISDA Product TaxonomyA classification scheme — a controlled vocabulary for labelling what KIND of derivative a trade isThis module

The taxonomy's origin is specific and regulatory: after the 2008 crisis, the Dodd-Frank Act (2010) required, for the first time, real-time public reporting of swap transactions in the US — subject to size-based masking for large ("block") trades. Regulators and Swap Data Repositories needed to bucket swaps into comparable categories, so a 5Y USD interest rate swap and a 5Y Brent crude oil swap wouldn't share the same block-trade threshold. Rather than every SDR inventing its own scheme, ISDA — the industry's own standards body — published a taxonomy everyone could converge on, freely available via isda.org.

Takeaway. The taxonomy classifies, it does not identify — the single most important distinction versus the UPI. A taxonomy path is a category label shared by every trade of that shape; a UPI is a specific issued code for one exact combination of economic terms within that category (Section 5 connects the two precisely).

02 · Structure

The Taxonomy Hierarchy — Four Levels, Five Asset Classes

A four-level hierarchy, one rung more granular than the "Product" layer in this curriculum's own Asset Class → Product → Instrument → Trade model.

Diagram · Four LevelsRestated & extended from Module 2 §7
Asset Class  ->  Base Product  ->  Sub-Product  ->  Transaction Type
======================================================================

Interest Rate      -> IRSwap     -> FixedFloat   -> Swap
Credit              -> SingleName -> Corporate    -> CreditDefaultSwap
Foreign Exchange    -> Forward    -> Deliverable   -> Forward
Equity              -> Swap       -> PriceReturn   -> Swap
Commodity           -> Energy     -> Oil           -> Swap

Each level narrows the category further left-to-right. A trade's
full "taxonomy path" is all four values read together -- none of
them alone is enough to identify the product.

There are exactly five official ISDA Asset Classes for derivatives — a short, closed list, distinct from the open-ended "Asset Class" values you'd see once cash instruments are included too.

ISDA Asset ClassPlain-English meaningExample Base Products
Interest RateCash flows depend on interest ratesIRSwap, FRA, Swaption, CapFloor, Cross-Currency Swap
CreditPayout depends on a default/credit eventSingleName, Index (CDX/iTraxx), TotalReturnSwap
Foreign ExchangePayout depends on currency ratesForward, Swap, Option, NDF
EquityPayout depends on a stock/index priceSwap, Option, VarianceSwap, Future
CommodityPayout depends on a physical commodity priceSwap, Forward, Option (Energy, Metals, Agriculture)
Callout — v1.0 vs v2.0. ISDA published an initial taxonomy (v1.0, ~2012) built for Dodd-Frank's real-time reporting categories — coarse, oriented around CFTC block-size rules. A more granular v2.0 (~2016) followed, aligned field-by-field with FpML (the industry's own XML messaging standard), adding finer sub-categories in places. Treat exact category names and which version a given system implements as something to confirm per-system — the same hedge this curriculum applies to the UTI generation waterfall §2 and SFTR §7's specifics.
Takeaway. The taxonomy is a classification tree, not a flat code list — "Swap" alone (Transaction Type) is ambiguous across all five asset classes, but Interest Rate / IRSwap / FixedFloat / Swap is not. The same principle SFTR §2's small, closed Type of SFT code set uses at one level of granularity — the ISDA taxonomy solves the same problem for a far larger, more varied universe of OTC derivatives.

Takeaway. Notice Transaction Type is "Swap" for three of five trades (Interest Rate, Equity, Commodity) — no single level of this hierarchy is sufficient alone. Also notice the Credit path's Sub-Product describes the reference entity's type, while every other asset class's Sub-Product describes an economic feature of the contract itself — the categories are genuinely asset-class-specific, echoing the UPI deep dive §3's point about reference-data templates.

04 · A common category error

Are Bonds and Cash Securities Ever Classified with ISDA Taxonomy?

No — the taxonomy classifies bilateral contracts, not deliverable things. A bond, share, or unit of commercial paper exists and can be held on its own; that's exactly why cash instruments use a different scheme entirely.

Cash Instruments (bonds, equities, MM)OTC Derivatives
What's being classifiedA deliverable thingA bilateral contract
Classification schemeCFI Code (ISO 10962), baked into most security mastersISDA Product Taxonomy (this module)
Instrument identifierISIN / CUSIPNo ISIN — UPI instead
Governing bodyISO, via National Numbering AgenciesISDA (industry trade body, Section 7)
Same Company · Two Classification WorldsNorthern Rail Corp
Northern Rail Corp 4.5% Bond 2030 (a cash instrument):
  ISIN: (issued by a National Numbering Agency)
  CFI Code: DBFUFR (illustrative -- debt, straight bond,
            fixed rate, registered)
  -> NO ISDA taxonomy field. It's a deliverable security, full stop.

5Y CDS on Northern Rail Corp (Module 2 §9, a derivative CONTRACT
that merely references the same company):
  Taxonomy path: Credit / SingleName / Corporate / CreditDefaultSwap
  -> NO CFI code, NO ISIN. It's a bilateral contract, classified
     by ISDA taxonomy, identified by a UPI instead of an ISIN.
Nuance — a derivative ON a bond still gets ISDA-classified normally. A bond option or bond future is itself a derivative contract and gets its own taxonomy path (typically Interest Rate or Credit) like any other OTC derivative — it's the underlying cash bond itself that never carries an ISDA classification, not "anything connected to a bond."
Takeaway. The fastest sanity check: if a record has an ISIN and a CFI code, it's a cash instrument and taxonomy fields should be empty; if it has a UPI and no ISIN, it's a derivative and taxonomy fields are mandatory. A rules engine that populates both, or neither, has a bug.

05 · Grammar vs. dictionary

How the Taxonomy Feeds Into the UPI — the DSB's Reference-Data Schema

The taxonomy and the UPI feel like the same thing because they genuinely are related — just at different layers of the same lineage.

Diagram · Industry Taxonomy to Issued IdentifierFull Lineage
ISDA PRODUCT TAXONOMY (this module)
  Industry-published classification scheme (v1.0 -> v2.0).
  A CONTROLLED VOCABULARY -- Asset Class / Base Product /
  Sub-Product / Transaction Type. No codes issued, no lookup
  system -- just the category definitions themselves.
       |
       v
CPMI-IOSCO TECHNICAL GUIDANCE (2017)
  Global regulatory standard-setters adopt ISDA's taxonomy
  structure as the BASIS for a harmonized product-classification
  framework every G20 jurisdiction's regulators could converge on.
       |
       v
DSB UPI REFERENCE-DATA SCHEMA (operated by ANNA-DSB, since 2022)
  Turns the taxonomy's categories into ACTUAL FIELDS on a live,
  queryable reference-data template per asset class -- and,
  critically, ISSUES A CODE (the UPI itself) for each unique
  combination of those fields.
       |
       v
EMIR / DODD-FRANK / OTHER REGIMES' TRADE REPORTS
  Consume the ISSUED UPI as a single mandatory field -- the
  reporting firm never re-derives the taxonomy path by hand.
Takeaway. Think of the ISDA Product Taxonomy as the grammar, and the UPI reference-data template as the dictionary built from that grammar. A reporting engineer never populates "ISDA Taxonomy" and "UPI" as two independently-derived fields on the same trade — the UPI's reference data already encodes the taxonomy path.

06 · Beyond the UPI

Where the Taxonomy Is Actually Used — Beyond the UPI

The taxonomy predates the UPI by roughly a decade and has several uses that have nothing to do with UPI reference data at all.

UseHow the taxonomy is actually consumedNotes
Dodd-Frank real-time public reporting (CFTC Part 43)Sets which block-trade notional threshold applies — separate thresholds per taxonomy categoryThe taxonomy's original reason for existing
Dodd-Frank recordkeeping (Part 45) & CFTC's own Swaps ReportSDRs bucket submitted swap data by taxonomy category for the CFTC's own market statisticsSame categories, different consumer
SEF / MAT determinationsA Made-Available-to-Trade determination is scoped in taxonomy terms (e.g. Fixed-Float USD IRS, given tenor buckets)Governs execution-venue obligations
CCP clearing-mandate determinationsPublished against taxonomy-shaped product descriptionsComplements Module 8 §5's clearing mechanics
UPI reference data (Section 5)Basis for the DSB's product classification fieldsThe newest use
Internal bank product mastersEvery OTC product template tagged with a taxonomy path at onboardingSection 8's practical IT view
Callout — EMIR doesn't literally name a field "ISDA Taxonomy." EMIR's own reporting technical standards (and the CPMI-IOSCO CDE fields it aligned to during REFIT) use their own product-classification fields — historically CFI-style, more recently the UPI itself — rather than a field literally labelled "ISDA Taxonomy." The category logic still traces back to ISDA's work (Section 5), but by the time it reaches an EU/UK report it's been absorbed into the UPI. The CFTC/Dodd-Frank rows above are where the taxonomy remains a directly-named, load-bearing concept.
Takeaway. The taxonomy's footprint is broadest and most explicit in the US Dodd-Frank/CFTC regime, while in the EU/UK EMIR world it survives mainly as the ancestry behind the UPI. Knowing which regime you're building for tells you whether "ISDA Taxonomy" needs to be a first-class field, or whether it only informs how you map a product to its UPI.

07 · Who changes it

Governance & Versioning

ISDA is an industry trade association, not a regulator or a live-operating market-infrastructure utility like ANNA-DSB — it publishes reference documents, it doesn't run a system.

Who Actually Changes the Taxonomy, and How
ISDA's own asset-class-specific working groups/committees
(member firms -- dealers, buy-side, infrastructure providers --
the same governance model that maintains the ISDA Master
Agreement itself, Module 12) periodically:

  -> propose new Base Products / Sub-Products / Transaction
     Types as new derivative structures emerge
  -> consult industry members on proposed changes
  -> publish a revised taxonomy version (v1.0 -> v2.0, and
     incremental updates) as reference documents on isda.org --
     free, not proprietary

-> ISDA does NOT mandate that anyone use the taxonomy. It becomes
   mandatory only where a REGULATOR (CFTC, under Dodd-Frank) or a
   downstream STANDARD (CPMI-IOSCO's UPI guidance, Section 5)
   requires its use.
Takeaway. The same infrastructure-vs-mandate distinction the UPI deep dive §4 draws for the DSB applies to ISDA here, one layer further upstream — "ISDA classifies this trade as X" is industry convention, not law; "the CFTC requires this trade's public report to use category X" is the regulatory mandate that actually makes it matter.

08 · Template, not per-trade

Configuring Taxonomy Values in Practice — the Product-Master View

The taxonomy path is a property of the product TEMPLATE, never re-derived or re-entered per individual trade — the same template-vs-instance pattern the UPI deep dive already established for UPI itself.

Product Master · Illustrative Static Reference DataBank Of Toronto
Product Name              | Asset Class | Base Product | Sub-Product | Txn Type
-------------------------------------------------------------------------------
CAD Fixed-Float IRS       | Interest Rate | IRSwap     | FixedFloat  | Swap
Single-Name CDS (Corp)    | Credit        | SingleName | Corporate   | CreditDefaultSwap
USD/CAD Deliverable Fwd   | Foreign Exch. | Forward    | Deliverable | Forward
Equity TRS (Price Return) | Equity        | Swap       | PriceReturn | Swap
Brent Crude Swap          | Commodity     | Energy     | Oil         | Swap

WHEN A TRADER BOOKS A NEW TRADE:
  1. Trade capture system asks "which product template?"
  2. Trader selects "CAD Fixed-Float IRS" (an EXISTING template)
  3. Taxonomy path flows onto the trade record AUTOMATICALLY from
     the product master row -- never manually typed by the trader
  4. Trade-specific fields (notional, tenor, counterparty, rate)
     do NOT affect the taxonomy path at all

IF THE DESK WANTS TO TRADE SOMETHING GENUINELY NEW:
  -> Product Control / New Product Committee classifies it against
     the taxonomy FIRST, creates a NEW product-master row, and only
     then can trades against that new template be booked
  -> Also the trigger for requesting a new UPI reference-data
     record from the DSB -- usually the same onboarding event

For a bond, the equivalent product-master row simply has no taxonomy columns populated at all — it carries a CFI code instead, because it's a security master entry, not a derivative product template.

Takeaway. Taxonomy Path belongs on the Product table, not the Trade table — trades inherit it by reference, the same way Module 2 §1's hierarchy establishes that product-defining attributes live at the Product layer. A system that lets the same product shape carry different taxonomy paths on different trades has a data-integrity bug, not a flexible feature.

Recap Quiz — Answers & Explanations

Check your work against these.

Q1 — The taxonomy classifies (a category label, e.g. Interest Rate/IRSwap/FixedFloat/Swap); the UPI identifies (a specific issued code for one exact combination of economic terms, built on the taxonomy's categories but adding Underlier, Notional Currency, Tenor)

Section 1's takeaway states this directly as the most important distinction to hold onto.

Q2 — "Swap" alone is ambiguous: it's the Transaction Type for Interest Rate, Equity, AND Commodity in Section 3's worked examples, so without the other three levels there'd be no way to tell a 5Y CAD IRS apart from a Brent Crude Oil Swap

Section 2's takeaway makes this point, and Section 3 demonstrates it concretely — three of five trades share the identical Transaction Type value.

Q3 — "Interest Rate / IRSwap / FixedFloat / Swap"; versus the Equity TRS's "Equity / Swap / PriceReturn / Swap," Base Product differs (IRSwap vs. Swap) while Transaction Type is identical ("Swap") for both
Section 3's worked-examples block lists both paths directly, flagging the shared Transaction Type as proof no single level suffices alone.
Q4 — No, the bond never gets a taxonomy path (it gets a CFI code instead); yes, the CDS does ("Credit / SingleName / Corporate / CreditDefaultSwap"), because the CDS itself is the bilateral contract being classified — the taxonomy classifies contracts, never the thing a contract references

Section 4's worked comparison walks through exactly this pair, with a nuance callout clarifying that even a derivative ON a bond still gets ISDA-classified normally.

Q5 — ISDA's taxonomy supplies the base vocabulary (no codes, no live system); CPMI-IOSCO's 2017 guidance adopts it as the basis for a global standard; the DSB operationalizes it into a live schema and issues a UPI per unique combination; EMIR/Dodd-Frank reports then consume that already-issued UPI

Section 5's lineage diagram states each layer explicitly, using the "grammar vs. dictionary built from that grammar" analogy.

Q6 — Any of: setting the block-trade notional threshold for Dodd-Frank real-time public reporting, bucketing swaps for the CFTC's own published market statistics, or scoping a SEF's MAT determination

Section 6's table lists all three as uses that predate, and are independent of, the UPI's 2022 introduction.

Q7 — No, ISDA is an industry trade association, not a regulator; using its taxonomy becomes mandatory only where an actual regulator (CFTC) or downstream standard (CPMI-IOSCO's UPI guidance) requires it

Section 7's diagram and takeaway state this directly, drawing the same infrastructure-vs-mandate distinction the UPI deep dive's Section 4 established for the DSB.

Q8 — On the Product record, not the Trade record — trades inherit the taxonomy path by reference; a system letting the same product shape carry different paths on different trades has a data-integrity bug

Section 8's product-master diagram ties this back to Module 2 §1's point that product-defining attributes live at the Product layer, not the Trade layer.
